# sdk-hypersparse-spmv-bfs — host-orchestrated BFS on the unmodified `sdk-hypersparse-spmv` kernel

Breadth-first search built by repeatedly launching the existing, unmodified
`hypersparse_spmv` CSL kernel from `../../spmv/sdk-hypersparse-spmv` and doing all BFS
bookkeeping (visited set, parent pointers, frontier masking, termination) on
the host. This is deliberately the naive construction — one kernel launch
per hop, full host round trip in between — built to make the cost of that
design visible before a fabric-resident version is attempted.

## Files

- `src/` — byte-identical copy of `../../spmv/sdk-hypersparse-spmv/src/` (kernel.csl,
  layout.csl, `hypersparse_spmv/`, `allreduce2R1E/`), for WSE-2. The CSL is
  **not** modified anywhere in this directory; the kernel still only knows
  how to compute one real-valued `y = A*x` per launch.
- `src_wse3/` — byte-identical copy of `../../spmv/sdk-hypersparse-spmv/src_wse3/`, for
  WSE-3 — see `../../spmv/sdk-hypersparse-spmv/README.md`'s "WSE-3 support" section for
  what differs from `src/` and why. `run_bfs.py` picks between the two based
  on `--arch`, same as `../../spmv/sdk-hypersparse-spmv/run.py`.
- `preprocess.py`, `memory_usage.py` — unmodified copies of
  `../../spmv/sdk-hypersparse-spmv`'s versions (same hypersparse compressed-column
  partitioning, same per-PE memory accounting). Shared by both
  architectures — matrix partitioning doesn't depend on arch.
- `cmd_parser.py` — `sdk-hypersparse-spmv`'s parser minus `--is_invec_one` /
  `--is_weight_one` (BFS always forces a 0/1 structural adjacency), plus
  `--source` (BFS root vertex).
- `run_bfs.py` — the new host driver: compiles/loads the kernel once, then
  loops `f_spmv` launches until the frontier goes empty.
- `commands_wse2.sh` / `commands_wse3.sh` — one-shot compile+run smoke test
  on `../../data/rmat4.4x4.lb.mtx` at a 4x4 grid, source vertex 0, one per
  architecture.
- `bfs_results.jsonl` — appended to on every `run_bfs.py` run (params +
  per-hop timings + verification result), not just printed to stdout.

## Design

### Boolean semiring via real arithmetic (no kernel change)

The kernel computes a real-valued multiply-add `y = A*x`; there is no
boolean AND-OR variant of it (contrast `../bool_diag_spmv`, which has its
own from-scratch kernel for exactly that). Rather than fork the kernel, this
version exploits that A's structural nonzeros are all `1.0` and the
frontier is `0.0`/`1.0`: `y[i]` becomes the *count* of frontier predecessors
reaching `i`, which is still exactly zero iff `i` is unreached this hop. The
host thresholds `y > 0` to recover the boolean OR a real semiring would
have computed directly on-device. This wastes a float multiply-add per edge
where one bit would do, but it means zero CSL changes were needed to get a
working BFS out of an SpMV kernel that was never designed for one.

### Directed graphs via a free transpose

Convention: `A[i, j] != 0` means a directed edge `i -> j` (row = source,
column = destination) — the standard mathematical adjacency-matrix
convention, and the one `scipy.sparse.csgraph.breadth_first_order(...,
directed=True)` also uses, which is what `run_bfs.py` verifies against.

Under that convention, one hop of *forward* BFS expansion is
`new_frontier = A^T @ frontier`, not `A @ frontier` — you want "which nodes
have an in-edge from the frontier", and `y = A*x` computes row-dot-x, i.e.
"which nodes have an out-edge into the frontier" (the wrong direction for
everything but a symmetric matrix). The kernel only ever computes `A @ x`,
so `run_bfs.py` feeds it `A^T`'s structure instead of `A`'s — and since a
transpose of a CSR is a CSC of the same matrix (and vice versa), this costs
nothing: `preprocess()` is called with `A`'s CSC passed as its `csrRowPtr`/
`csrColInd` argument and `A`'s CSR passed as its `cscColPtr`/`cscRowInd`/
`cscVal` argument. No matrix rebuild, no extra memory. For an
undirected/symmetric matrix `A == A^T`, so this is a no-op relabeling — the
directed and undirected cases are the same code path in `run_bfs.py`.
(All the matrices generated by `../../benchmarks/gen_rmat.py` are symmetrized,
so this only matters if you bring your own directed `.mtx` file.)

### Parent reconstruction is a host-side afterthought

OR-reducing a hop tells you a node *became reachable*, not *which frontier
member reached it* — that needs a "select a witness" semiring (e.g.
min-index-of-predecessor), which this AND-OR-via-real-arithmetic kernel
does not implement. So for every node newly set in a hop, `find_parents()`
separately scans its incoming edges — against the *original* `A` (not the
transposed structure fed to the device) — and picks whichever predecessor
happens to already be in the previous frontier. Correct visited/level
information falls out of the device computation for free; parent pointers
require this separate O(in-degree) host-side pass per new node. This is a
genuine limitation of building BFS-with-parent-tracking on top of a bare
boolean SpMV, not an implementation shortcut — a smarter on-device semiring
is what would remove it.

### The ping-pong requirement, and why it doesn't remove the host round trip

See the comment on `y_local_buf` in `hypersparse_spmv/pe.csl`: feeding `y`
back as the next `x` (`spmv(x, y); spmv(y, x)`) only compiles if
`local_vec_sz == local_out_vec_sz`. Since `A` is square (`nrows == ncols`)
and this driver requires a square PE grid (`pcols == prows`, same
`assert` `../bool_diag_spmv` makes for its own reasons), that equality holds
automatically — no special-casing needed.

That equality is necessary but not sufficient for a *direct* ping-pong,
though: `x` is distributed column-block-then-row-block
(`dist_x_to_hwl`) while `y` is distributed row-block-then-column-block
(`unpad_3d_to_1d`'s inverse) — deliberately different layouts, inherited
unchanged from `../../spmv/sdk-hypersparse-spmv`. So even with matching block sizes, a
hop's `y` can't be copied directly into the next hop's `x_tx_buf` in place;
it has to be flattened back to a plain 1-D vector on the host and
re-distributed via `dist_x_to_hwl`. That host repack is where the
visited-mask is applied anyway, so it isn't wasted motion — but it does
mean "the ping-pong works" doesn't imply "the host can stay out of the
loop", which is worth being explicit about before assuming a fabric-only
future version could reuse this layout as-is.

### Host loop

Per hop, `run_bfs.py`:

1. distributes the current frontier (0/1 `float32`) into the PE grid and
   `memcpy_h2d`s it into `x_tx_buf`;
2. launches `f_spmv` (blocking);
3. `memcpy_d2h`s `y_local_buf` and reassembles it into a flat length-`n`
   vector;
4. thresholds `> 0`, masks out already-`visited` nodes
   (`new_mask = candidate & ~visited`);
5. if `new_mask` is empty (popcount == 0), stops — no more reachable nodes;
6. otherwise assigns parents for the newly-visited nodes, folds them into
   `visited`, and uses `new_mask` as the next hop's frontier.

## Requirements

- **Square matrix** (`nrows == ncols`) — this is a graph adjacency matrix.
- **Square PE grid** (`pcols == prows`) — required for the ping-pong
  argument above.
- `prows >= 4` — inherited from `hypersparse_spmv/layout.csl`'s own
  `@comptime_assert`.

## Status

Working, verified against `scipy.sparse.csgraph.breadth_first_order` (exact
visited-set match; parent pointers checked for validity rather than exact
match, since BFS parent choice is inherently non-unique) on both `--arch
wse2` and `--arch wse3`. Not yet measured
against `../bool_diag_spmv` or a hypothetical fabric-resident version —
that comparison, and quantifying the per-hop host-round-trip overhead this
design deliberately incurs, is the next step (see `../../benchmarks/`).
